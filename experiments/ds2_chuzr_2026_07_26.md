# DS2 CHUZR — leaving-row selection with dual steepest edge

**PROVENANCE: SOURCE-INFORMED (HiGHS). Not a clean-room result.**

Built after reading `HEkkDualRHS.cpp` / `HEkkDual.cpp` under the 2026-07-25
owner authorisation recorded in `docs/PROVENANCE.md`. No HiGHS code was
copied. The shipped dual simplex was not modified, not linked and not
rebuilt; every shipped-solver number below comes from instrumentation and
parameters that already exist (`phase_us`, `leaving_rule`).

---

## Verdict

**The hypothesis is dead, and it is dead twice over.**

The brief funds a cheaper CHUZR on the argument that HiGHS can afford dual
steepest edge because its leaving-row selection is cheap — a maintained
hyper-sparse infeasibility list against linprogx's full dense *m*-row scan.
Both halves fail on measurement:

1. **The scan is not the cost.** The shipped AVX2 CHUZR scan costs
   **5.33 µs/pivot** on greenbea against a **143.8 µs** pivot — **3.7%**.
   Exact DSE costs **+109.7 µs/pivot**. A *zero-cost* CHUZR funds **4.9%**
   of DSE. The lever is off by a factor of **21**.
2. **The maintained list is slower than the scan it replaces — everywhere.**
   Against the shipped AVX2 scan the component costs **1.61x** more on
   greenbea, **3.68x** on 25fv47, **5.05x** on degen2. Even its *scan
   alone*, ignoring all maintenance, never wins: 1.08x–2.08x worse.

The component is *correct*: over **30,749** real CHUZR states across
greenbea, 25fv47 and degen2 it selected a row of **identical merit to the
shipped dense scan on every single call** — zero disagreements, zero audit
failures. It is correct and it is not worth having.

**The valuable result is the third one, which the brief did not ask for and
which contradicts its premise.** "Exact DSE is worse than Dantzig" is a
*greenbea-only* fact that was generalised into a class fact. Swept across all
nine simplex-routed cells on the shipped solver, unmodified, **DSE wins the
trajectory on seven of nine and loses on greenbea — the one cell the verdict
was taken on**:

| instance | prior loss | Dantzig (ships) | exact DSE | HiGHS target | DSE vs Dantzig |
|---|---:|---:|---:|---:|---:|
| 25fv47 | 2.74x | 8,300 | **2,614** | 3,033 | **3.18x fewer** |
| degen2 | 2.69x | 1,447 | **653** | 537 | **2.22x fewer** |
| greenbeb | 1.82x | 8,919 | **5,633** | 4,910 | **1.58x fewer** |
| greenbea | 1.55x | **4,399** | 4,675 | 2,836 | 0.94x — worse |
| tuff | 1.27x | 221 | **183** | — | 1.21x fewer |
| israel | 0.97x | 234 | **121** | — | 1.93x fewer |
| fffff800 | 0.81x | **345** | 372 | — | 0.93x — worse |
| agg2 / agg3 | 0.51x / 0.48x | 274 / 272 | 261 / **260** | — | 1.05x |

On 25fv47 exact DSE takes linprogx **below HiGHS's own pivot count** — using
machinery already in the shipped C, behind an existing parameter, switched
off by default. Four of the five losses that motivated this rewrite are
largely closed by it on trajectory. Whether that converts to wall is decided
by the +109.7 µs/pivot above, not by anything in CHUZR.

**And the brief's prime suspect is not the mechanism.** Candidate-list
staleness: zero wrong selections in 30,749 states. Weight drift: the
Forrest–Goldfarb recurrence holds to machine epsilon (median error 9.8e-15
over 4,394 greenbea pivots); its error tail does widen ~275x from the first
half of the trajectory to the second, which is the predicted shape, but
**0.0% of pivots ever reach HiGHS's 0.25x rejection threshold.** §4b.

## 1. What was built

`src/linprogx/_ds2_chuzr.{c,h}` — self-contained C99: no `Python.h`, no
linprogx headers, no dependency on the shipped solver, builds and runs on
its own. `ds2_chuzr` matches the fixed signature in `docs/DS2-REWRITE.md`
exactly; `pricing_state == NULL` gives the stateless dense reference with
identical selection semantics.

What was taken from HiGHS — understood and reimplemented, not copied:

| mechanism | HiGHS | here |
|---|---|---|
| per-row infeasibility maintained, not rediscovered | `HEkkDualRHS.cpp:310-372` | `viol[]`, `ds2_chuzr_rows_changed` |
| updated only over the FTRAN pattern | `updatePrimal` :310-350 | same |
| candidate list of infeasible rows | `workIndex/workMark` | `list`/`mark` |
| merit cutoff, rebuilt on demand | `createInfeasList` :432-513 | `ds2_build_list` |
| dense fallback when too many rows are infeasible | `workCount = -numRow` :505 | `dense_mode` |
| randomised scan start that wraps | `chooseNormal` :60-63, :80-83 | `random_start` |
| weight floor 1e-4 | `SimplexConst.h:162` | `weight_floor` (default 1e-4) |
| re-selection ban list | `HEkkDual.cpp:1449-1490` | `ds2_chuzr_ban` |

**One deliberate deviation, recorded because it matters.** HiGHS's cutoff
thresholds are absolute: build a cutoff above 500 candidates, keep
`max(0.001·count, 500)` of them, abandon the list above `0.2·m`. At the *m*
of this campaign's whole simplex-routed class (415–2,392) those cannot hold
at once — 500 candidates already exceeds `0.2·m`, so any list long enough to
earn a cutoff is immediately abandoned for a dense scan and the cutoff
branch is structurally unreachable. Expressed as fractions of *m* the same
mechanism is reachable and can be measured rather than assumed. These are
global constants; nothing is fitted to an instance.

## 2. How it was measured

Two harnesses, neither of which touches the shipped solver.

**`experiments/ds2_chuzr_validate.py`** runs a self-contained
bounded-variable dual simplex (scipy `splu` per pivot, logical `B = -I`
start, HiGHS-style Phase-1 bound swap over a homogeneous RHS) on the
presolved instances. At every pivot it hands the real state — `basis`,
`x_B`, `lo_ext`, `hi_ext`, edge weights — to
`experiments/ds2_chuzr_bench.c`, which runs the component and both shipped
reference scans (scalar and AVX2, transcribed from `_csparse.c:14566-14606`
and `:12647-12746`) inside rdtscp brackets. **The component's answer drives
the trajectory**, so these are counts with it substituted in.

Measurement discipline, for a box at load 40 on 12 threads:

- **Medians, not sums.** A bracket that spans a context switch reads tens of
  thousands of extra ticks; a handful of those dominate any mean. Every
  variant is sampled per call and the report quotes medians.
- **Rotated order.** Four variants take turns going first, so the
  first-touch cold-cache cost does not accrue to one side.
- **An in-situ floor.** A bracketed no-op is measured in the same rotation.
  It reads **144 ticks (0.040 µs)** — 2.4% of the smallest figure below, so
  nothing here is a timer artefact.
- **The maintained array is audited** against a full recompute every 250
  pivots. Zero failures across all runs.
- Cycles and pivot counts only. No cross-process wall comparisons.

**`probe_out/ds2-chuzr-phase-share.json`** reads the `phase_us` buckets the
shipped solver already returns, under `leaving_rule` 1 and 5. A ratio of two
buckets inside one process survives load drift.

## 3. Cost — µs per CHUZR call, medians over real states

TSC 3.593 GHz. `DS2 total` = the scan plus the incremental maintenance the
scan depends on; charging only the scan would be dishonest.

| instance | rule | *m* | DS2 scan | DS2 maint. | **DS2 total** | shipped scalar | **shipped AVX2** | DS2 vs AVX2 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| degen2 | Dantzig | 415 | 3.52 | 5.03 | **8.55** | 6.74 | **1.69** | **5.05x worse** |
| degen2 | DSE | 415 | 2.49 | 1.81 | **4.30** | 4.88 | **1.70** | **2.52x worse** |
| 25fv47 | Dantzig | 726 | 4.32 | 5.55 | **9.87** | 11.65 | **2.69** | **3.68x worse** |
| 25fv47 | DSE | 726 | 4.57 | 4.31 | **8.88** | 11.76 | **2.90** | **3.07x worse** |
| greenbea | Dantzig | 1525 | 5.73 | 2.85 | **8.58** | 36.87 | **5.33** | **1.61x worse** |
| greenbea | DSE | 1525 | 6.91 | 4.59 | **11.50** | 41.03 | **5.88** | **1.96x worse** |

The component beats the *scalar* scan on greenbea by 4.3x. That is not the
comparison that matters: `ds_simd_on` defaults on and `leaving_rule` 1 and 5
both take the AVX2 path (`_csparse.c:14551-14559`), so **AVX2 is what
ships**.

Two structural reasons it loses, both visible in the table:

- **Maintenance costs more than it saves.** The FTRAN pattern averages 135
  rows per pivot on greenbea (8.9% of *m*) and 316 on 25fv47 (43.5%).
  Recomputing those violations costs 2.85–5.55 µs — comparable to, or more
  than, a complete AVX2 rescan of every row.
- **A candidate list turns a streaming scan into a scattered one.** The
  AVX2 scan streams `x_B` contiguously with hardware prefetch, 4 lanes wide:
  ~12 ticks/row. The list scan chases scattered indices into
  `viol`/`sig`/`ban`: ~130 ticks/entry on greenbea. Sparsity must beat a
  ~11x per-element handicap before it wins. At a median list length of 107
  of 1,525 rows — a 14x sparsity ratio — it is still only break-even on the
  scan alone (1.08x worse), and the maintenance then sinks it.

HiGHS's structure is not wrong. It is sized for a different *m*. At
*m* = 1,525 there is nothing left to save: the thing being replaced already
costs 5.33 µs.

## 4. Selection quality

**Equivalence — the component changes nothing.** Across all six runs the
component and the shipped dense scan selected rows of identical merit on
**30,749 of 30,749** states (artifacts `probe_out/ds2-chuzr-main.json`,
`probe_out/ds2-chuzr-degen2.json`):

| run | states | identical merit | identical row | pivots to optimality |
|---|---:|---:|---:|---:|
| degen2 Dantzig | 2,828 | 2,828 | 2,821 | 2,826 |
| degen2 DSE | 1,042 | 1,042 | 1,035 | 1,040 |
| 25fv47 Dantzig | 12,417 | 12,417 | 12,413 | 12,415 |
| 25fv47 DSE | 3,177 | 3,177 | 3,175 | 3,175 |
| greenbea Dantzig | 6,889 | 6,889 | 6,753 | 6,887 |
| greenbea DSE | 4,396 | 4,396 | 4,394 | 4,394 |
| **total** | **30,749** | **30,749** | **30,591** | |

The 158 row differences are merit *ties* resolved differently; the merit is
identical in every one. Selection is therefore **neutral** — substituting the
component perturbs no trajectory, so iterations to optimality are exactly
those of the rule it implements. All six runs reached optimality. A further
two ablation runs with the candidate list disabled entirely (`DS2_LIST_OFF`,
4,051 more states) also agreed on every call, bringing the audited total to
**34,800 states, zero disagreements, zero audit defects**.

**Iterations to optimality**, shipped solver, unmodified, `leaving_rule` 1
(Dantzig, the shipped default) against 5 (exact Forrest–Goldfarb DSE, the
merit this component implements). Both certificate-backed optimal at
eps = 2e-5:

| instance | Dantzig | DSE | ratio | Dantzig wall | DSE wall |
|---|---:|---:|---:|---:|---:|
| greenbea | 4,399 | 4,675 | 1.06 | 0.638 s | 1.191 s |
| 25fv47 | 8,300 | 2,613 | **0.31** | 1.559 s | **0.491 s** |
| degen2 | 1,447 | 653 | **0.45** | 0.156 s | **0.108 s** |

The greenbea pair reproduces the ledger's 4,399 / 4,675 exactly, which is
the cross-check that this harness reads the shipped solver correctly.

**DSE wins the trajectory on seven of nine, and loses on greenbea — the one

Four of the five losses are largely closed by a rule that already ships,

The wall column has to be read carefully, because the +109.7 µs/pivot of §5
is what buys those pivots — and **single-shot wall on this box cannot resolve
it**. A first pass read degen2 as 178 → 50 ms and a second, minutes later, as
146 → 161 ms: the same comparison, opposite signs. Pivot counts were bit-
identical across every repeat.

across the five, which is the honest error bar):

| instance | Dantzig median | DSE median | DSE speedup | run-to-run spread |
|---|---:|---:|---:|---:|
| degen2 | 146 ms | **48 ms** | **3.0x** | 1.3x / 1.5x |
| 25fv47 | 1,747 ms | **740 ms** | **2.4x** | 1.2x / 1.7x |

The gap is outside the spread on both, so on these two the rule pays for its
own per-pivot premium. On the two *m* = 2,392 instances it does not — greenbeb
3,272 → 5,000 ms and greenbea 1,628 → 2,150 ms, single-shot and therefore
only indicative, but consistent with +109.7 µs/pivot outweighing a 1.58x
pivot reduction at that size. **Whether DSE is a net win is decided by
`pricing_update`, not by the selection**, and settling it properly needs the
paired multi-host protocol, not this box.

Within the validation driver — a different formulation, logical basis plus a
Phase-1 bound swap instead of the shipped crash basis and big-M — DSE beats
Dantzig on **greenbea too**, 4,394 against 6,887. Those numbers are not
comparable to the shipped ones and prove nothing on their own, but they are a
hint that greenbea's DSE anomaly may belong to the starting basis rather than
to DSE.

## 4b. The prime suspect: does pricing quality decay on long trajectories?

The brief's prime suspect is that our dual simplex degrades as the trajectory
lengthens — "weight drift, degeneracy handling, or candidate-list staleness."
Two of those three are directly measurable here.

**Candidate-list staleness: measured, and it is not happening.** 30,749 of
30,749 states selected identical merit (§4), the maintained violation array
was audited row-for-row against a full recompute on a stride with zero
defects, and the merit cutoff's rebuild-and-rescan guard fired 7 times in
4,396 greenbea pivots — every time recovering the true argmax.

**Weight drift: measured, and it is not the mechanism either.** For the
selected row the exact edge weight is `‖rho‖²`, and rho is already in hand
every pivot, so the ratio stored/exact is free to record. Over full DSE
trajectories (`probe_out/ds2-chuzr-drift.json`):

| | samples | median \|ratio−1\| | p99 | max, 1st half | max, 2nd half |
|---|---:|---:|---:|---:|---:|
| greenbea | 4,394 | 9.8e-15 | 4.3e-06 | 8.9e-03 | **2.46** |
| 25fv47 | 3,175 | 2.0e-13 | 4.9e-06 | 5.6e-02 | **0.54** |

- **The Forrest–Goldfarb recurrence does not drift.** Median error is machine
  epsilon; p99 is 4e-6. It is an exact algebraic identity and it behaves like
  one.
- **The tail does widen with trajectory length** — the worst error grows ~275x
  from the first half of greenbea to the second. That is the shape the brief
  predicted, and it is the first time this campaign has put a number on it.
- **But it never reaches where it would matter.** Across every decile of both
  trajectories, **0.0%** of pivots fall below HiGHS's 0.25x rejection
  threshold or above 4x. HiGHS's acceptance test would never have fired.
  That independently explains the ledger's finding that re-selection has zero
  effect — it is not that the test is redundant with our gamma_r anchoring
  alone, it is that **there is nothing in range for it to reject.**

One caveat, and it is the live lead: the driver refactorises every pivot, so
it cannot exercise LU-update error — the classical source of DSE drift in a
solver carrying Forrest–Tomlin updates across a 50–100 pivot refactorisation
interval. **That is the version of the drift hypothesis still standing, and
testing it needs ds2_core, not this component.**

## 5. Why the lever cannot work — the arithmetic

Shipped `phase_us`, greenbea, µs per pivot:

| bucket | Dantzig | DSE | delta |
|---|---:|---:|---:|
| `pricing_update` | 0.87 | 48.75 | **+47.88** |
| `pivot_row` | 31.02 | 48.72 | +17.70 |
| `ftran_col` | 27.80 | 40.62 | +12.82 |
| `btran_rho` (contains the CHUZR scan) | 28.52 | 39.22 | +10.70 |
| everything else | 55.59 | 76.19 | +20.60 |
| **total** | **143.80** | **253.50** | **+109.70** |

DSE's cost is `pricing_update` — the extra `lu_ftran(lu, rho, dse_tau)` the
Forrest–Goldfarb recurrence needs (`_csparse.c:15660`) — plus the knock-on
cost of a denser trajectory. **It is an FTRAN, not a scan.** The CHUZR scan
lives inside `btran_rho` and is bounded above by the 5.33 µs measured
directly in §3.

> Budget available to CHUZR: **≤ 5.33 µs/pivot**.
> Cost of DSE: **109.70 µs/pivot**.
> A free CHUZR pays for 4.9% of it.

Note also that the `leaving_scan` bucket the shipped solver reports reads
0.000 µs and must not be quoted as the scan's cost: `DS_TICK(1)` fires only
on the cost-shift and phase-restart paths (`_csparse.c:14660`, `:14718`),
so the ordinary CHUZR scan is folded into `btran_rho`. That is why §3
measures the scan directly instead of reading a bucket.

## 6. What actually follows

**Kill the cheap-CHUZR lever.** It is measured, it is small (3.7% of a
pivot), and the proposed replacement is 1.6x–5.1x *worse* than what ships.
Do not spend further on the leaving-row scan at these problem sizes. The
component is left in the tree, gated behind nothing and wired to nothing, as
the record of the measurement.

**Do not kill the leaving-row rule.** The ledger's "exact DSE is worse"
verdict was taken on greenbea and generalised. It does not generalise: on
the full sweep (§4a) DSE wins the trajectory on **seven of the nine**
simplex-routed cells and loses on greenbea — the one cell the verdict came
from. 25fv47, degen2, greenbeb, tuff and israel all take large pivot wins
from a rule already present in the shipped C, behind an existing parameter,
off by default. On 25fv47 exact DSE beats HiGHS's own pivot count.

The immediate, cheap follow-up is therefore **not new code**: re-measure the
board with `leaving_rule=5` on the simplex-routed cells under the paired
multi-host protocol (`tools/modal_bench.py`). Nothing here is board-grade —
the wall figures are single-shot on a loaded box — but the pivot counts are
load-invariant and they are large. If the per-pivot premium holds at the
measured +109.70 µs, the rule should win on the small-*m* losses and lose on
the two *m* = 2,392 ones, which is a testable prediction rather than a hope.

The question this leaves — and the one worth funding next — is not "how do
we make CHUZR cheap" but **"can the DSE τ-solve share work with the entering
column's FTRAN?"** `pricing_update` at 48.75 µs against a `ftran_col` bucket
of 40.62 µs prices the extra solve at roughly its fair value, so the only
structural saving left in DSE is fusing the two solves. That is a core
question, not a CHUZR one.

## 7. What I did not establish

- **The driver is not the shipped solver.** Its pivot counts (greenbea
  6,887 Dantzig / 4,394 DSE) differ from the shipped solver's (4,399 /
  4,675) because its ratio test, refactorisation cadence and tolerances
  differ. It exists to generate *real states*; the equivalence claim rests
  on those states only, never on its trajectory matching. The authoritative
  pivot counts in §4 come from the shipped solver.
- **The box was at load 40 throughout.** Medians plus a 144-tick in-situ
  floor make the comparison sound, but the absolute µs are
  memory-bandwidth-starved and would shrink on an idle machine. The verdict
  rests on the streaming-versus-scattered *ratio*, and contention hits both
  sides.
- **Two estimators, same verdict.** The §3 table is a ratio of medians. The
  stronger paired statistic — the median of per-call ratios, both halves
  measured microseconds apart on the same state, which cancels common-mode
  noise — was computed separately and agrees: shipped AVX2 over DS2 total
  reads 0.67x / 0.74x on greenbea, 0.31x / 0.41x on 25fv47, 0.19x / 0.40x on
  degen2 (Dantzig / DSE). Every value is below 1, i.e. the shipped scan is
  faster, by 1.35x to 5.3x. Interestingly the paired *scan-only* ratio does
  favour the component on greenbea (1.16x / 1.39x) — the list works where the
  FTRAN pattern is genuinely sparse (8.9% of *m*); it is the maintenance that
  then loses the win.
- **These *m* only** — 415 to 1,525 after presolve. HiGHS's list structure
  would very plausibly win at *m* in the 10⁵ range. That is not this
  campaign's class.
- **The nine-cell sweep is single-run, presolved, and not board-grade.** It
  calls the dual simplex directly after presolve — the shipped auto route's
  stall-rescue shape (`sparse.py:240`) but not every route the board uses —
  and the wall figures in it are single-shot on a loaded box. The pivot
  counts are load-invariant and are what the §4a conclusion rests on; the
  wall figures are quoted only where the gap is multiples of the drift band.
- **The drift probe cannot see LU-update error.** The driver refactorises
  every pivot, so it measures the recurrence in isolation. Drift arising from
  Forrest–Tomlin updates across a real refactorisation interval is untested
  and remains the one live form of the decay hypothesis.
- **The component was never run inside the shipped solver.** Substitution is
  argued from per-state selection equivalence over 30,749 states, not from a
  linked build. That is exactly as strong as the equivalence, and no
  stronger.

## 8. Reproducing

```bash
UV_CACHE_DIR=/tmp/uv-cache uv sync --extra dev --no-build-isolation
UV_CACHE_DIR=/tmp/uv-cache uv pip install --reinstall -e . --no-build-isolation

# cost + equivalence on real states  -> probe_out/ds2-chuzr.json
PYTHONPATH=. uv run python experiments/ds2_chuzr_validate.py \
    --instances degen2 25fv47 greenbea --rules dantzig dse

# shipped-solver rule sweep and phase profile
PYTHONPATH=. uv run python experiments/ds2_chuzr_rule_sweep.py
```

```bash
cc -O2 -std=c99 -Wall -Wextra -fPIC -shared \
   -o build/ds2/libds2chuzr.so \
   src/linprogx/_ds2_chuzr.c experiments/ds2_chuzr_bench.c -lm
```
