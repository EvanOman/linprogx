# K1 — Instruction-throughput census of the DS hot loops (2026-07-19)

**Verdict: LIVE.** Every ≥20%-of-wall slice on both the cold and the B\* greenbea
trajectories runs far under IPC 2 — BTRAN at IPC ≈ 0.30 and FTRAN at ≈ 0.60 (each
~20% of wall), with PRICE/ratio/rcost at 1.05–1.51. Achieved IPC is 0.30–1.51
against a ~4 issue-width ceiling; vector ratio is 0% (the shipped kernels are
scalar SSE2 — `-O3` without `-march=native`, and the loops are index-chased so
they would not auto-vectorize regardless). The untested seam the dossier flagged
is real: the hot loops are throughput-starved, not just cache-bound.

This is the master measurement. It does not itself change the kernels; it tells
K2–K12 where the headroom is and how large it is.

## Method (rdtsc + objdump fallback; honest about the sandbox)

`perf_event_paranoid = 4` blocks `perf stat`/`perf record` (CPU-event access is
denied without CAP_PERFMON), and valgrind/callgrind are not installed. Per the
dossier this forces the rdtsc-cycle + instruction-estimate fallback:

- **Cycles per slice**: an env-gated (`LINPROGX_DS_K1_CENSUS=1`) parallel rdtsc
  accumulator was hung on the existing `DS_TICK` phase-transition macro in
  `CSRMatrix_solve_eq_box_dual_simplex`, giving per-phase TSC cycles for all 13
  buckets with zero new reads inside any inner loop.
- **Dynamic iteration / nnz counts**: cheap loop-header counters (per row / per
  pass / per active column — never per element) for the pivot-row scatter, ratio
  scan, reduced-cost update, and every dominant triangular-solve / eta inner
  loop. A single process-global solve-inner counter is snapshotted by `DS_TICK`,
  so BTRAN and FTRAN inner work is attributed to their phases automatically.
- **Instructions per iteration**: read directly from `objdump -dl` of a
  codegen-neutral `-g -O3` build (the `-g` was reverted after mapping; it does
  not change codegen — measurements reproduce bit-for-bit without it).

**Off-path safety.** Every counter and rdtsc read is guarded by the runtime
census flag; with the flag off the solve math and trajectory are untouched.
Verified: census OFF and ON give identical pivot counts and bit-identical
objectives on both trajectories.

**TSC caveat (conservative).** TSC here is constant/nonstop and runs at the
3.593 GHz base clock (measured: total census cycles ÷ total census wall =
3.593 GHz on both trajectories, matching the Ryzen 5 3600 base). Under load the
core boosts above base, so **reported IPC (instructions ÷ TSC cycles) is an
upper bound on true retired IPC** — the low-IPC finding is robust to the caveat.

**Branch misses: not measured.** Hardware branch-miss counters need perf (blocked)
or a simulator (absent). I report objdump branch *density* and predictability
instead; the LIVE verdict rests entirely on the IPC arm, which is measured.

**Trajectories.** Cold = native crash start (4,399 pivots). B\* = the P3
homogeneous auxiliary basis (min c'x s.t. Ax=0, lower-only in [0,1], boxed in
[0,0]), solved once via highspy's public API as an oracle (no solver source read)
and injected through the diagnostic warm-start hook (3,334 pivots, 0 repairs, 0
fallback). Both use the shipped greenbea config `leaving_rule=1, expand=1,
bfrt=0, tol=1e-8`. 7 reps each, medians reported. All correctness gates pass
(status optimal; reduced objectives match P3 to the reported digits; reduced
residual ≤ 4.8e-7).

## What the assembly shows (objdump, `-g -O3`, x86-64 baseline)

- **Zero packed-double / AVX instructions in the entire DS function** (`grep ymm`
  = 0; 47 incidental `*pd` from compiler zeroing vs 1,143 scalar `*sd`). `-O3`
  targets baseline x86-64 (scalar SSE2); no `-march=native`.
- **PRICE scatter** (`alpha_scratch[col] += rho_val*csr[p]`): per element a
  32-bit index load, a gathered `movsd` of `alpha_scratch[col]`, a data-dependent
  `ucomisd 0 → jp/jne` first-touch branch, scalar `mulsd`+`addsd`, scatter store.
  14 insns on the revisit path, 21 on first touch (weighted ≈ 16/element).
  Measured 10.7 cyc/element ⇒ latency/dependency-bound, IPC ≈ 1.5.
- **Triangular solves** (dense `lu_ftran`/`lu_btran` L/U passes + `lu_btran_sparse`
  inline lt/ut + FT eta apply): inner axpy is 11 scalar insns —
  `movslq idx; movsd val; mulsd x[j]; movsd x[i]; subsd; movsd store`. The
  gathered read-modify-write of `x[i]` creates serial store→load chains
  (the same row updated by many columns), which is why BTRAN runs at **36 cyc
  per axpy** (IPC 0.30) and FTRAN at 18 (IPC 0.60) despite a cache-resident
  working set.
- **ratio scan** is contiguous over `alpha_scratch[j]` but carries 4–6
  data-dependent branches per column plus a `divsd` (13–14-cycle latency) on
  every admissible column, so a "cheap" sequential scan still costs ~11 cyc/it.

## Projection arithmetic vs the dossier flip targets

Cold flip target: **≤ 54 us/pivot (−40%** from 90.5). Idealized ceiling if each
slice's IPC were lifted to 2.0 (cycles scale by IPC\_now/2):

| slice | %wall | IPC now | wall saved if →IPC 2 |
|---|---:|---:|---:|
| BTRAN | 20.7 | 0.30 | 17.6% |
| FTRAN | 20.0 | 0.60 | 14.0% |
| PRICE | 18.9 | 1.51 | 4.6% |
| ratio | 15.5 | 1.30 | 5.4% |
| rcost | 10.0 | 1.41 | 3.0% |
| **total** | | | **≈ 44.6%** |

44.6% off 90.5 ⇒ **≈ 50 us/pivot**, which *clears* the −40% cold target. **The
theoretical headroom to hit the flip target exists entirely inside these six
slices, and ~71% of it is in the two triangular-solve slices (BTRAN+FTRAN).**

Caveats on the projection: IPC 2 on the dependency-bound solves is optimistic —
the serial RMW chains cap ILP, so K3's dense-SIMD solve bodies must actually
break those chains (block/panel updates), not just widen the arithmetic. A
conservative "capture half the headroom" still yields ~22% ⇒ ~70 us/pivot, short
of cold's target but exactly in the B\*-path window (65–72 us/pivot). Net: the
census says the *budget* is there; realizing it is K2/K3/K4/K5's problem.

### Where each downstream angle should aim (evidence-ranked)

1. **K3 (dense-SIMD BTRAN/FTRAN bodies)** — highest value. 40% of wall at IPC
   0.30–0.60; the biggest gap from the ceiling. Must break the axpy RMW serial
   dependency, not merely vectorize it.
2. **K2 (branchless SIMD PRICE scan)** and **K4 (SIMD ratio)** — ~19% and ~15.5%
   of wall at IPC 1.3–1.5, data-dependent branches + (ratio) `divsd`. Real but
   smaller headroom than the solves.
3. **K5 (scan+update fusion)** — PRICE (18.9%) + rcost (10.0%) touch the same
   dense alpha vectors twice; fusion attacks memory traffic on ~29% of wall.
4. **K12 (compiler/`-march=native`)** — the 0% vector ratio is partly a missing
   `-march=native`; contiguous slices (ratio scan, dense-U tails) could pick up
   auto-vectorization for free, though the index-chased scatters will not.

## Kill criterion & verdict

Kill criterion (dossier): LIVE if any ≥20%-of-wall slice runs under IPC ~2 or
>5% branch misses. **BTRAN (20.7% wall, IPC 0.30) and FTRAN (20.0% wall, IPC
0.60) each satisfy the IPC arm by a wide margin on both trajectories; PRICE,
ratio and rcost reinforce it at 1.05–1.51.** No slice is anywhere near IPC 2, let
alone the ~4 ceiling. **Verdict: LIVE.**

Honesty ledger: (a) reported IPC is an upper bound on true retired IPC (TSC ≤
core clock) — conservative for a low-IPC claim. (b) Branch-miss rate is not
hardware-measured; branch density is reported instead and the verdict does not
depend on it. (c) The solve inner-iteration counter omits the FT spike/eta
linked-list chain walks; if those add work, true solve IPC rises slightly toward
~1 but stays well under 2 (and BTRAN/FTRAN remain the most-starved slices).
