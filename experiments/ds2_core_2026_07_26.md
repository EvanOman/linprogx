# will replace

**Status: the core is built and correct.** DS2 reaches `optimal` with a
certificate on greenbea, 25fv47 and degen2, and on **all 40** LPnetlib
instances swept — including four the shipped dual simplex cannot solve at all —
with objectives matching the published optima, using deliberately naive stubs

the shipped solver's pivot count, median 1.13x. That gap is the point: the
stubs are Dantzig and a textbook Harris test, and components A and B are what
close it.

The shipped dual simplex is untouched: trace digest `679168a4baad36d6`, 4,399
pivots on greenbea, re-verified after every change in this wave.

## 1. What was built

`src/linprogx/_ds2_core.c` — a complete bounded-variable dual simplex, reached
two ways, both default OFF:

| entry | how |
|---|---|
| `LINPROGX_DS2=1` | routes `solve_eq_box_dual_simplex` to DS2 |
| `matrix.solve_eq_box_ds2(c, b, lo, hi)` | calls DS2 directly |

The gate is four lines at the top of the shipped entry point and is the only
line of it that changed.

Components plug in **by file presence**, not by editing anything:

```c
#if __has_include("_ds2_chuzr.c")     /* component B, when it lands */
#  include "_ds2_chuzr.c"
#else
#  include "_ds2_stub_chuzr.c"        /* Dantzig placeholder          */
#endif
```

so `_ds2_chuzr.c` / `_ds2_chuzc.c` appearing in `src/linprogx/` is the whole
integration step. The shared contract is `_ds2_iface.h`, unchanged.

### The three things DS2 does differently, and why

**1. Logical form, unconditionally.** The right-hand side is carried in the
bounds of the logical columns — `lo[n+i] = hi[n+i] = -b_i` — and the simplex
system's RHS is identically zero. Row `i` reads
`sum_j A[i,j] x_j + x_{n+i} = 0`, so `x_{n+i} = -b_i` reproduces `Ax = b`. This
was verified result-identical on the shipped path (4,399 pivots) before this
wave. It is the prerequisite that makes phase 1 a bound swap: with the RHS
living in bounds, overwriting the bound arrays deletes `b`, and there is
nowhere else for it to hide.

**2. No big-M anywhere.** The shipped path buys initial dual feasibility by
parking one-sided columns at an invented bound `1e5 x scale` away — 93.4% of
greenbea's columns — which turns a dual-*sign* problem into a huge
primal-*distance* problem and then has to pay a certification tax on the way
out: a gap-damage budget over every parked column, the non-committal
`dual_unbounded_boxed` downgrade whenever any artificial bound exists, and a
documented "retry with M x 100 once, then give up". DS2 establishes dual
feasibility by the phase-1 bound substitution instead, so:

- an empty ratio test is a **genuine** primal-infeasibility certificate;
- optimality is tested against the true bounds with **no artificial bound
  present at all**;
- the entire damage-budget/retry path does not exist.

**3. Phases are data, not control flow.** There is no `if (phase == 1)` in the
iteration body. Phase 1 substitutes a bound table keyed only on which true
bounds are finite (`[0,1]` lower-only, `[-1,0]` upper-only, `[0,0]`
boxed/fixed, `[-1000,1000]` free); phase 2 restores the true bounds; the same
loop runs on the same basis, the same factorization and the same weights.

### The loop

```
setup     Ruiz (gated on inf-norm ratio >= 100, as shipped)
          logical form, save true bounds for all n+m columns
          basis: singleton-cascade crash (default) or B = I
          factorize, identity fallback, transposes
          y = B^-T c_B, r_j for all nonbasics
          phase = (dual infeasibilities among one-sided/free columns) ? 1 : 2
          install phase-1 boxes if phase 1; place every nonbasic on the side
          its reduced cost wants -- always possible in phase 1

per pivot 4a  x_B = B^-1 (0 - A_N x_N)          [only when marked stale]
          4b  ds2_chuzr  -> leaving row, sigma
          4c  rho = B^-T e_r                    [hyper-sparse BTRAN]
          4d  pivot row  = scatter of rho over A's CSR rows (+ logicals)
          4d' ds2_chuzc  -> entering column, theta_dual, bound flips
          4d" apply flips: one batched column-space delta, one FTRAN
          4e  alpha_col = B^-1 a_q              [hyper-sparse FTRAN]
          4f  primal step
          4g  r_j -= theta_dual * alpha_j over the pivot row's support
          4h  ds2_pricing_update (before the basis changes)
          4i  basis bookkeeping
          4j  Forrest-Tomlin update; refactor on failure, violent pivot,
              lu_should_refactor, or every 500 pivots; on refactor,
              recompute duals and repair dual feasibility

exit      phase-1 optimality  -> restore true bounds, re-place, continue
          phase-2 optimality  -> CLEAN-STATE AUDIT (below)
          empty ratio test    -> infeasible (certified)
          accepted            -> refactorize, recompute, re-certify in
                                 ORIGINAL units against the TRUE bounds
```

### The clean-state audit

Reaching primal feasibility is not optimality, because the working problem may
carry anti-degeneracy cost shifts and reduced costs the Harris band has let
drift. So the phase-2 "optimal" branch trusts nothing:

1. strip **every** cost shift, recompute the duals from the factorization;
2. re-test every nonbasic against the true bounds;
3. a wrong-signed reduced cost with an opposite finite bound is repaired by a
   **flip**, which changes no duals;
4. a wrong-signed reduced cost with **no** opposite bound is a genuine dual
   infeasibility only pivoting can fix — so **phase 1 is re-entered** to drive
   it out;
5. if neither fired, the basis is optimal.

The phase-1 re-entry is bounded at 20 rounds and exhausting it reports
`dual_infeasible`, not a fabricated optimum. On greenbea, 25fv47 and degen2 the
re-entry never fires — phase 1 reaches a dual objective of 0 (or −9.6e-11) and
the residual shifts all sit below the certification tolerance. It does fire, and
converge on the first round, on 25fv47 under the `B = I` start (one unfixable
column at 4.7e-05). It is the mechanism that turns a would-be wrong answer into
either a right one or an honest `dual_infeasible`, and both of those beat
certifying a suboptimal basis.

## 2. Two bugs found, both worth recording

### 2.1 The phase-1 stale-reduced-cost bug — the one that mattered

Under the phase-1 bound map **every boxed and fixed column becomes
`FIXED` at `[0,0]`**. The shipped solver's reduced-cost update skips `FIXED`
columns — correctly, because on that path a fixed column stays fixed for the
whole solve and its `r` is never read again. In DS2 that assumption is false:
phase-1 "fixed" is temporary, and a boxed column's reduced cost is *exactly*
what decides which side it is placed on when the true bounds come back.

Symptom: phase 1 terminated correctly (dual objective 0), then the first
phase-2 refactorization measured a **max reduced-cost drift of 2.1e+05**, the
drift-repair shifted costs by that much to restore "feasibility", and phase 2
proceeded to solve a completely different LP. greenbea produced 757 unfixable
dual infeasibilities per audit round and never converged. The instrument that
found it was one line: compare the recomputed `r` against the carried `r_ext`
at every refactorization and print the max.

Fix: update `FIXED` columns too, and refresh their `r` at every refactorization.
greenbea went from *not converging in 100,000 pivots* to **5,235 pivots,
certified optimal**.

### 2.2 A tiny pivot is not a reason to give up on the pivot

Before the fix above, 96,458 of greenbea's ~97,000 phase-2 iterations hit
`|alpha_col[r]| < 1e-12` while the pivot row claimed `|alpha_row[q]| >= 1e-9`
for the same pair. That
disagreement is only possible when the basis representation has degraded. The
first response — skip and continue — re-picked the same row forever.

The contract's row-ban protocol is the right answer: write
`DS2_WEIGHT_BANNED` into `weights[leaving_pos]`, leave the basis alone, and let
the next refactorization lift the ban. The one trap is that a fully banned
CHUZR returns `basis_pos = -1`, which looks exactly like optimality — so the
core refactorizes and looks again before believing it, bounded at 20 rounds.
With 2.1 fixed, zero rows are banned on any measured instance.

### Starting basis: crash vs. logical (B = I)

HiGHS starts from `B = I` because that is the unique basis on which exact
steepest-edge weights are free. linprogx's singleton-cascade crash starts much
closer to primal feasibility. With the stub components the crash wins on
average:

| instance | crash (default) | logical B = I |
|---|---:|---:|
| greenbea | **5,235** | 6,956 |
| degen2 | **1,615** | 2,081 |
| sierra | **779** | 1,390 |
| 25fv47 | 10,242 | **7,838** |
| greenbeb | 10,226 | **8,616** |

3–2 for the crash, and it wins the required cells. **This is a stub-conditional
result and should be re-measured once component B lands** — the whole argument

not use weights at all. `LINPROGX_DS2_LOGICAL_BASIS=1` keeps the switch live.

### What did not move the needle

While chasing the stale-`r` bug of §2.1 the obvious numerical suspects were

|---|---|
| refactorization interval 500 -> 50 | identical failure (801 unfixable columns either way) |

That both were flat is what ruled out "accumulated drift" and pointed at a
structural defect instead — the drift instrument then found it in one run.

## 4. Honest verdict

**The loop is right. It is not yet fast, and it was never going to be at this
milestone.**

What is genuinely established:

- DS2 solves and **certifies** all 40 instances swept, with objectives matching
  the published optima and residuals at or below the shipped path's.
- **Deleting big-M is worth something on its own.** Four cells the shipped dual
  simplex cannot solve — grow7/15/22 at the iteration limit, scsd8
  `dual_infeasible` — DS2 solves in 279 / 890 / 1,071 / 2,949 pivots to the
  published optimum. Those are the one-sided-column-heavy models where parking a
  variable at `1e5 x scale` costs thousands of full-price pivots to undo.
- The certificate is *stronger* than the shipped path's: with no artificial
  bounds anywhere, an empty ratio test is a real infeasibility certificate and
  the exit test is a plain dual-feasibility check in original units, with no
  gap-damage budget and no big-M retry standing between the answer and the
  claim.
- The phase-1 bound substitution works end to end and reproduces the phase-1
  pivot count measured independently on the shipped path.
- The component seams are real: the core never inspects pricing or ratio-test
  state, and both stubs are swapped in by adding a file.

What is not established, and should not be claimed:

- **No performance claim.** On the cells both solvers certify, DS2 is a median
  1.13x behind the shipped solver on pivots (worst 1.79x) and behind it on
  wall. The rewrite's premise is that the *coupled* pivot-selection regime is
  where the deficit lives; this milestone deliberately fixes the loop while
  leaving selection naive, so it says nothing about whether the premise holds.
- **The per-pivot cost has not been measured or protected.** linprogx's 1.73x
  per-pivot advantage over HiGHS is the thing the campaign must not trade away.
  DS2's kernels are the same ones (same hyper-sparse BTRAN/FTRAN, same CSR
  scatter, same Forrest-Tomlin update), but it does not yet have the SIMD CHUZR
  or the cached candidate list, and the loaded box makes the wall numbers here
  worthless for that question. It needs the within-process alternating A/B
  before anyone says anything about it.
- **greenbea is not closed.** 5,235 pivots against HiGHS's 2,836 is worse than
  the shipped 4,399. Nothing about the board changes.

### One deliberate behavioural difference in the result dict

DS2 returns `y` in **original units** (`R y_scaled`); the shipped path returns
the scaled duals when Ruiz fires. DS2's convention is the one its own exit
certificate uses — `r_j = c_orig_j - a_j^T (R y)` against the true bounds — and
it is what makes that certificate meaningful, so it is not something to
"fix" back. The two agree whenever Ruiz is skipped, which is the common case.
Flagging it because anything downstream that consumes `y` from both entry
points would otherwise see an unexplained scale factor.

### One interface gap worth flagging to the orchestrator

`ds2_pricing_update` receives `rho` and `alpha_col` but **not**
`tau = B^{-1} rho`, and components have no LU access. The Forrest–Goldfarb dual
steepest-edge recurrence needs exactly that one extra FTRAN. Component B can
therefore implement Devex but not exact DSE without an amendment — either an
extra `tau` argument (the core would compute it only when asked, so the FTRAN
stays off the critical path when it is not) or an LU-solve callback. I did not
change `_ds2_iface.h`, because the other two components may already be building
against it and a silent divergence is worse than a flagged gap.
